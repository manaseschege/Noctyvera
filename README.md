# Nightgals — web client

React 19 + Vite + Ant Design 6 front end for the **Nightgals API** (Spring Boot, JWT bearer auth).

```bash
npm install
npm run dev      # http://localhost:5173
npm run build
```

The dev server proxies `/api` to the backend, so the browser stays same-origin (no CORS) and the ngrok interstitial is bypassed. Point it elsewhere with `VITE_API_TARGET` in `.env.local`:

```
VITE_API_TARGET=https://your-tunnel.ngrok-free.dev
```

Spec: `{backend}/swagger-ui/index.html` · raw: `{backend}/v3/api-docs`

## How the product works

**Two account types, and they are different products.** `/join` asks which before it asks for anything else.

**Viewers** are asked for an email and a password and nothing else. No profile, no date of birth, no documents, and nothing to buy to get in. `nextStep` is `BROWSE` forever, every onboarding guard waves them through, and they pay only when they find a creator they want to see.

**Creators** walk a funnel:

| Stage | `nextStep` | What's possible |
|---|---|---|
| Registered | `CREATE_PROFILE` | Fill in the profile |
| Profile saved | `SUBMIT_KYC` | Submit a document + selfie |
| Submitted | `AWAIT_REVIEW` | Wait for a moderator |
| Rejected | `RESUBMIT_KYC` | Fix and resubmit |
| Approved | `DONE` | Buy a package, then post and go live |

A viewer who changes their mind calls `POST /me/become-creator` and keeps their handle, purchases and history.

The username is **generated by the server** at registration (`BoldZebra720`). Members can reroll it but not choose it.

### Signing in takes two screens

`/login` takes the password and gets back a *challenge*, not a session. A six-digit code goes to the account's inbox and `/verify` exchanges it for tokens.

The challenge lives in the auth store, so `/verify` is unreachable without one and a reload sends you back to `/login`. `CodeInput` handles the parts people notice only when they are missing: pasting the whole code from the email, backspacing out of an empty cell into the previous one, arrow keys, and `autocomplete="one-time-code"` so phones offer it. Filling the last cell submits — no button press in the common case.

Where the server has codes switched off, `/login` returns tokens directly and the flow skips `/verify` with no change to the calling code.

### Paying — viewers pay creators

**One payment, one creator, all of her content.** No photo tier, no video tier: a viewer picks a person, not a menu.

**Each creator sets her own price**, so there is no single figure to hardcode. It arrives on her feed card and her profile as `unlockPriceMinor` / `unlockPriceDisplay`, and `CheckoutModal` charges that, falling back to the platform default only for an object that predates the field. Creators set theirs in `/studio/account`.

A subscription still covers everyone, while it runs.

Whatever a creator marked `FREE` is her shop window and is visible to anyone, signed in or not; her `EXCLUSIVE` posts come back with `locked: true` and no URL, so nothing leaks client-side.

### Paying — creators pay the platform

Publishing needs a package, bought at `/onboarding/package` and managed at `/studio/packages`:

| | Covers | Allowance |
|---|---|---|
| **Bronze** | photos only | small |
| **Silver** | video only | small |
| **Gold** | photos and video | large |

`GET /billing/creator-packages/mine` answers the only question the studio needs — `canPostPhotos` and `canPostVideos` already fold together "does the package cover this type" and "is there room left". `MyPackage` draws the two allowances as meters, because "you cannot upload" has two different causes and two different fixes.

Checkout is **asynchronous**. `POST` returns a `CheckoutResponse` with an `action`:

| action | Client does |
|---|---|
| `REDIRECT` | Navigate to `redirectUrl` |
| `PROMPT_ON_PHONE` | Show "check your phone", poll until it settles |
| `MANUAL` | Show `instructions`; an admin settles it by hand |

Every purchase starts `PENDING`. `CheckoutModal` polls `/billing/purchases` until it flips to `COMPLETED` or `FAILED` rather than assuming the money moved.

## Layout

```
src/
  api/            one module per backend area — nothing else talks to the network
    config.js       API base, enums mirrored from the OpenAPI spec, upload limits
    http.js         fetch wrapper: bearer token, auto-refresh on 401, error mapping
    auth.js         register/login/logout, /me, profile, username
    kyc.js          draft -> upload documents -> submit
    members.js      browse, profiles, their media and live sessions
    media.js        own media: upload, caption, primary, delete
    billing.js      plans, unlocks, subscriptions, entitlements, settlement polling
    live.js         directory, playback, hosting
    admin.js        KYC queue, media queue, payments, grants
  components/
    Guards.jsx      route guards driven by nextStep and verificationStatus
    CheckoutModal   the paywall
    MemberCard  MediaTile  SmartImage  layout/  charts/  ui.jsx
  pages/
    public/         Landing, HowItWorks, NotFound
    auth/           Login, Register
    onboarding/     CreateProfile, Verify, Status
    app/            Discover, MemberProfile, LiveDirectory, LiveRoom
    me/             MyMedia, MyLive, MyBilling, MyAccount
    admin/          KycQueue, MediaQueue, Payments
  store/auth.js   session + entitlements (zustand)
```

### Auth handling

`http.js` owns the token lifecycle: it attaches the bearer token, and on a 401 it calls `/auth/refresh` once and replays the request. Parallel 401s collapse into a single refresh. When the refresh token is finally dead, subscribers to `onAuthExpired` clear the session and the guards bounce to `/login`.

## Staff console

`/admin`, open to `MODERATOR` and `ADMIN`:

- **Identity review** — the KYC queue, with both document sides and the selfie, duplicate and date-of-birth mismatch warnings, and an under-18 block. Approve or reject with a typed reason.
- **Payments** (ADMIN only) — settle or fail manual payments, and grant access without one.

That is the whole console. Media review was removed: posts publish the moment a verified creator uploads them, so there was no queue to work — only after-the-fact spot-checking, which is not a job anybody was doing. The takedown endpoints (`POST /admin/media/{id}/takedown`, `/restore`) are still there and still the right remedy for something illegal; they simply have no screen in front of them.

**Payments normally need no admin either.** With the server's default provider a purchase is `COMPLETED` before the checkout response is written and `action` comes back `NONE`, so the client grants access immediately instead of opening a waiting screen. The Payments queue matters when the server is switched to the manual provider.

## Notes for the backend team

### Anonymous browsing (pending)

The shop window is meant to be public: a visitor with no account should be able to
browse members, see the free preview photos and clips, the profile picture, and enough
detail (handle, age, city, vibe, bio, locked counts) to decide whether to pay.

Today these return **401** with no token:

| Endpoint | Now | Needed |
|---|---|---|
| `GET /members` | 401 | public |
| `GET /members/{userId}/profile` | 401 | public |
| `GET /members/{userId}/media` | 401 | public, `locked: true` on everything past the free preview |
| `GET /live` | 401 | public |

`GET /live/{id}/playback` and everything under `/me` and `/admin` should stay authenticated.
The paywall doesn't weaken: locked items already come back without a `url`, so an anonymous
caller sees the same teaser a signed-out browser is supposed to see, and nothing more.

The client is already built for this — the pages are on public routes and simply render an
`AccessGate` while the API refuses. **When the endpoints open up, no frontend change is
needed**; the same code starts showing real content.

### One other finding

**`GET /me` returned 500 for any account with a profile** (reproducible, survived re-login) during the first integration pass. It was working again later the same day. `authApi.me()` keeps a fallback that reconstructs the session from the cached `AuthResponse` plus `/me/profile` on any 5xx, so a repeat won't lock users out. Remove that fallback once you're confident it's fixed — it's marked with a comment.

Also worth confirming: `previewPhotoUrls` on `MemberCardResponse` are relative media ids in some responses; the client resolves anything non-absolute through `/media/{id}/file`.

## Design

Dark theme — near-black canvas, champagne-gold accent, Cormorant Garamond for headings, Inter for UI and all figures. Tokens live in `src/theme.js` (Ant Design `ConfigProvider`) and `src/styles/global.css`. Charts are hand-rolled SVG with a crosshair readout and a single accent hue — no chart dependency.

Demo imagery resolves through `fallbackDataUri` in `src/components/placeholder.js` (a deterministic gradient) wherever the backend has no file yet. Real member photos come from the API.
